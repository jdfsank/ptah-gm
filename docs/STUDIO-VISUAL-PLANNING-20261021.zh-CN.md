# 每轮策划反馈的视觉策划

后续分图规划与批次路径见 [分图规划与确认生成](STUDIO-IMAGE-PLAN-BATCHES-20261021.zh-CN.md)。下文保留上一轮单图实现和验收历史；其中“不新增任务类型”等描述不适用于后续分图实现。

日期：2026-10-21。适用：Studio 的初始策划、澄清、READY、后续讨论及冻结后的概念检查。

## 使用路径

1. 在策划反馈旁点击“开启视觉策划”。初始想法区也保留可折叠入口；已有方案在项目标题旁提供快捷入口。方案的两个入口都会将面板滚动到可见位置并聚焦面板，按钮同步显示展开状态；收起后焦点返回入口。后台状态更新及刷新已提交依据不会重复滚动或抢走输入焦点。
2. 展开“已提交依据”，核对项目、方案修订、反馈位置和材料。编辑“本次视觉说明”，再展开实际提示词。
3. 手动点击 ImageGen 按钮，生成一张低质量、1536×1024 的检查图。打开、收起、刷新和切换项目只读取记录。
4. 结果默认仅供检查。选择“纳入下轮参考”后填写采纳用途、需要保持和尚未确定的内容，形成对应修订的参考草稿。
5. 澄清阶段完成必答问题，通过“提交回答”一次提交回答与参考。READY 阶段可合并补充与参考，也可只提交参考变更；均创建待重新策划的新修订。

策划执行中可以查看上次反馈和已有图片。冻结后及制作期间仍可检查、手动出图和保留参考草稿；活动制作期间不能直接提交参考修订。后续满足创建修订条件时，用户才能提交；已有制作结果的后续调整通过迭代草稿统一申报。归档项目只提供查看。

参考草稿不等于采纳。存在未提交参考变更时，冻结入口要求先提交重新策划，或明确撤销参考草稿。查看和出图都不改变方案或冻结输入。

## 生成依据与来源

服务端提供以下可选择的材料：原始已提交需求、与原始需求不同的本轮调整、当前可查看的策划反馈、最近 12 条已提交讨论、当前方案及已采纳参考用途。未提交回答、READY 补充和工作台草稿不自动进入依据；“本次视觉说明”仅影响这次出图。

实际提示词上限为 32000 个 Unicode 字符，与现有 ImageGen 包装器一致。超限时必须显式取消部分材料后重新核对，系统不会静默截断，也不会创建模型 session 来摘要。界面预览与服务端使用相同材料顺序和文本。

每张图永久保留生成时的项目、方案、修订、反馈位置、反馈所属修订、所选材料快照和最终提示词。当前讨论更新后，旧图继续显示原来源；即使重新采纳，也不会变成新版方案的生成证据。

图像用于概念、风格、轮廓、灯光与构图核对。玩法规则、精确数值、碰撞和运行效果仍须核对文字方案并通过实际游戏验证。

## API 与兼容

`GET /api/projects/{projectId}/proposals/{proposalId}/visual-context` 返回已提交材料、实际提示词组成部分、长度上限和来源定位。该接口不生成、不创建策划 session。

原有 `POST /api/projects/{projectId}/concept-references` 的五字段初始概念请求保持兼容。方案入口仍使用该接口，在五字段之外成组增加：

```json
{
  "requestId": "客户端持久化的唯一编号",
  "sourceText": "",
  "interpretation": "本次视觉说明",
  "size": "1536x1024",
  "quality": "low",
  "source": {
    "proposalId": "proposal-…",
    "proposalRevision": 3,
    "feedbackId": "discussion:5",
    "contextVersion": "服务端返回的不透明版本标识"
  },
  "materialIds": ["original", "feedback", "plan"]
}
```

`feedbackId` 使用服务端讨论数组的从零开始索引；首轮尚无反馈时为 `initial`。客户端不得自造材料文本或修改版本标识。`contextVersion` 由已持久化的当前方案及原始需求方案事件身份组成；同修订内容更新也会失效，不依赖时间戳精度或独立校验和。

服务端先检查请求编号：同编号、同项目、同请求内容只返回原记录。新编号必须通过项目归属、来源版本、材料选择、长度和归档状态检查；旧来源返回 `REFERENCE_SOURCE_STALE`，不会派发 ImageGen。结果保留 `sourceSnapshot`、`prompt` 和 `promptVersion=2`；素材的 `generation.provenance` 保留来源身份。

初始概念和方案入口共享控制器、持久化请求状态、轮询和原编号核账；同项目已有未决请求时不允许新请求。不确定的通信结果保留原编号，恢复后先核账；刷新不自动重投。确定的 4xx 拒绝显示失败，来源过期要求重新核对。

方案变更继续使用已有 `proposal.revise`：澄清回答、READY 补充、`assetRefs` 和 `visualReferences` 通过同一个带版本预期的命令原子提交。无新增后台策划 session 类型，无新增图片自动采纳路径。

## 实现位置

- `backend/visual_planning.py`：材料提取、选择快照、提示词与长度规则。
- `backend/concept_references.py`：来源核验、幂等请求、共享生成流程与素材来源。
- `backend/studio_protocol.py`：已提交讨论的反馈修订身份；沿用原子修订协议。
- `frontend/studio/visual-planning.js`：可折叠面板、材料与提示词预览、修订草稿和概览/详情卡。
- `frontend/studio/studio.js`：共享生成控制器、回答/补充提交、冻结拦截、同修订刷新后的身份检查。
- `frontend/studio/visual-feedback.jsx`：React 卡保留图片原来源；配套生成的 JS 已更新。
- `tools/studio_frontend.py`：正式静态服务允许加载新模块。
