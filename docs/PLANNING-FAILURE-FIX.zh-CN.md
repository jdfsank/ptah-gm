# 工作台策划诊断与恢复修复

日期：2026-10-09。范围为通用工作台的策划生命周期、诊断、状态恢复和提交保护。未实现、批准或制作具体游戏。

## 原生诊断结论

一次生产策划在 420.009 秒后超时，响应为空，受管进程组停止已确认。原生 stderr 显示响应流断开、解码异常和重连失败。使用原输入的复测同样在 420.005 秒后停止，没有计划输出。原后端虽保存了私有 `session.json`，但失败分支没有把原生证据与可读诊断保留到提案 API，前端因此只显示笼统失败，且误用“制作失败”状态名称。

保持原模型、服务和参考输入，仅将服务管理的只读策划回合设为 `medium` 后，第三次执行在 420.003 秒超时。它已返回完整且通过对象协议校验的 `NEEDS_CLARIFICATION` JSON，但未收到 `item/completed` 或 `turn/completed`。不能据此宣称原生回合完成，也不能将其中的对象计划作为可制作方案。该次记录没有原生错误通知；缺少完成事件的外部原因仍未确定。

## 通用修复

- 原生证据在判定状态、解析响应前保存到提案；旧失败记录可只读补全显示。界面只呈现固定诊断文案、耗时、session、原生状态和停止确认。
- 驱动保留最多 20 条原生错误摘要、终止 turn 的错误和最多 40 条安全 item 生命周期事件，便于区别连接中断、残缺输出与完成事件缺失。
- 策划使用服务预设的 `medium`，制作继续继承原设置。仅服务构造参数能选择推理强度，packet 不能覆盖；全局配置、模型、服务地址、凭据和代理均未修改。
- 超时只允许恢复经过完整协议校验的澄清问题。进程停止、权限回调、执行记录与只读目录都必须通过检查。恢复清空对象文档和任务，保留 `planningEvidence.status=timeout` 并显示明确提醒，制作确认继续禁用。
- 历史恢复使用现有 reconcile 接口，核对最新提案、发布基线、原进程组、原始请求全部不可变字段及盘上结果。重复恢复幂等；旧输入漂移、较新提案和不确定执行均拒绝恢复。
- 重试保留原项目、文字、参考图和结构化修改；网络异常或 HTTP 5xx 后锁定重试，要求刷新核账。不会因为响应丢失立即重复创建策划。
- 刷新和项目选择恢复该项目最新的失败诊断或未完成提案，防止旧失败覆盖新计划或显示另一项目的策划。
- 页面重开时将待处理提案与其项目快照一同恢复；刷新优先保留当前项目，旧作业不能把选择切回另一项目。概念阶段不再误显示为已验证的工程基线。
- 澄清回合优先仅输出问题，完整对象计划留到答复之后。下一回合清理陈旧页面诊断，私有原生回合文件继续保留。

## 实际恢复边界

使用第三次已保存的完整响应恢复了两道澄清问题，没有重新提交输入。API 确认为 `NEEDS_CLARIFICATION`、修订 1；原文字及三项参考输入保留，`document=null`、`tasks=[]`、制作表单数 0、作业数 0。原生状态仍为 `timeout`。用户回答后才进入新的策划回合，完整计划仍需单独确认。

生产原生文件包含私有输入，留在本机状态存储中，不加入 Git 报告。报告不复制用户文字、参考图片、模型配置或凭据。恢复也不代表上游响应流问题已经解决。
