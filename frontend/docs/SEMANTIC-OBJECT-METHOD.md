# 通用语义对象拆分方法 v1.0

## 目标与边界
对象是人可以识别、解释、修改、复用或独立验证的游戏概念。文件、节点、ECS Entity、组件、贴图和动画数量都不能直接决定对象数量。一个对象可以跨多个文件；一个文件也可以支持多个对象。

交付物不是完整新引擎。它是可审计的语义清单、来源/影响关系、编辑能力声明和基于该清单生成的工作台。本仓库的中立模型不依赖 Godot、战斗、主角或 DNA 的必填叙事。当前项目适配器是人工审阅后的、显式规则驱动的快照提取器，不声称任意项目自动理解。

## 1. 先定范围，再收集证据
冻结源版本、目标运行版本、纳入和排除目录。逐项声明“发现了什么 / 映射了什么 / 能在何处编辑 / 验证到哪一层”。先列输入、系统、数据、资源和默认/自动/失败路径，再列对象，避免从美术栏反推游戏。

必须交叉检查：设计文档、场景/数据表、代码与配置、输入、资源绑定、状态/生命周期、运行日志与测试。只有文档的内容标为 intent；读到实现标为 fact（静态）；推断标为 inference；未实现改动标为 proposal。不能把测试文件存在当成测试通过，也不能把浏览器预览当成引擎运行。

## 2. 用边界问题筛选候选
- 玩家、自动行动敌人、NPC、宠物等都可为活动对象。输入不是对象存在的前提。
- 移动平台、机关、门、投射物、特效可为环境/支持对象。静止或无贴图也不妨碍独立识别。
- 会话、关卡规则、进度、经济、任务、UI 可以是非实体语义对象。
- 询问：它承担什么职责？谁拥有状态？谁写位置？能否独立替换/复用/验证？修改它会影响谁？
- 当状态/生命周期和修改影响范围不同，拆分；当拆开只增加技术噪声而没有独立操作意义，合并为关联属性。
- 不因同一贴图而合并行为不同的对象；不因三份文件而把同一对象拆成三个。

例：骷髅荷官和幽灵荷官共享 SpriteFrames，但攻击距离、接近与攻击策略不同，保留两个定义。门的可见图像、触发区域与目标引用属于门的关联面；背后的场景迁移服务则是规则对象。拼图方块可以由拖拽驱动，旋转/吸附/成功判定不必套用攻击三段式。故事节点可以没有运动、贴图和独立叙事文本，却有进入条件、选项和后果。

## 3. 对象内部的关联层
对象本体 → 驱动 → 行为 → 状态/生命周期 → 运动 → 表现。
这些是可选的关联面，不是要求每个对象都填满的层级树。
- 本体：稳定语义 ID、名称、角色/职责、边界、所有者、引用关系。
- 驱动：玩家、AI、事件、时间、物理，可组合。
- 行为：continuous（连续）、action（离散主动）、response（被动响应）、interaction（交互）、rule（规则）。
- 状态/生命周期：进入条件、退出/中断、默认、恢复、创建/销毁、成功和失败路径。运行时字段和配置参数不能混为一谈。
- 运动：速度、加速度、路径、碰撞、位置写入者。运动不等于动画；没有动画的投射物也能移动。
- 表现：图像、动画剪辑、姿态、音效、VFX、UI 提示。相同动画可覆盖多个状态；缺失剪辑应明确保留缺失。

视图按行为类型产生：连续运动显示输入→目标速度、加速和边界；离散动作有阶段时才显示时间线；被动响应显示触发→反应→恢复/终止；交互显示条件→目标→结果；规则显示状态转换和守卫。不能把所有行为强塞成前摇/生效/后摇。

## 4. 明确区分四个层次
1. Definition：共享定义，改动影响所有引用。
2. Placed instance：场景实例，只改变局部位置/覆盖。
3. Spawn rule / marker：生成条件或定位标记，不是额外角色。
4. Ephemeral runtime instance：引擎当前产生的短命对象，不应伪装成可永久放置的资源。

工作台可以展示前 3 层和第 4 层的规则，但只有真正接入运行时才能声称看到了实时实例。持久玩家与各房间入口必须分开；玩家的动作不挂在某个 start 标记上。

## 5. DNA 是三个观察面
Design 解释机制/规则/参数，Narrative 解释设定/意图/玩家感知，Art 解释呈现/资源绑定。三者引用同一语义对象 ID，不是三个对象库。Narrative 可缺省；文档摘意和编辑者推断应与事实分开。不能为了栏目整齐补造设定。

## 6. 来源、写入和影响必须双向
每个对象/行为/实例/规则拥有 sourceRefs；来源包含快照文件、行/JSON 路径、哈希和证据类别。源项→语义项 ledger 用于找遗漏；语义项→sourceRefs 用于发现无证据项。

implementation（实现状况）、mapping（映射精度）、editability（只读/浏览器草稿/提案/写回）和 verification（静态/模型/DOM/引擎）独立记录。一个已实现对象可以暂时只读，一个可编辑浏览器字段也不意味着源文件支持写回。无来源的项只能是显式提案，不得伪装已实现或可写回。

影响关系至少覆盖：实例引用、共享资源复用、规则读写方、生成/销毁方。编辑前展示“全局共享”或“当前实例”；批量修改作为一次事务，可撤销；旧修订提案不能覆盖新改动。

## 7. 无损与覆盖验收
未编辑导入应语义等价于输入，未映射原始字段必须保留；若只做局部快照，应缩小导入声明。任何源写回必须有 no-op round trip、目标字段差异、未知字段保留、引用正确性和引擎验证。没有这样的适配器就只导出概念计划，不标作 Godot 可导入文件。

覆盖报告必须写出分母：当前适配器覆盖的是哪些文件、输入、声明状态、绑定资源、场景记录。每条记录为 mapped、excluded（理由）或 unmapped（后续决定），不能以“0 unmapped”宣称全游戏语义穷尽。文件级拥有者归属不等于每个内部变量或动态路径都被验证。

## 实施结构
- dist/semantic-model.js：轻量中立验证、默认草稿和兼容迁移
- tools/extract-velvet.py：当前项目显式适配器，验证锚点并重新生成 catalog/证据快照
- dist/semantic-data.json：统一语义清单；对象/行为/实例/生成规则/ledger/sources
- dist/evidence/：可点击的源快照行，不是活的代码编辑器
- fixtures/：拼图、故事两个无战斗最小契约样例
- tests/semantic-qa.cjs：正反向覆盖、能力声明、迁移和中立模型测试

接入下一个游戏时只替换项目适配器和源清单，复用验证器/视图类型/checklist；允许扩充语义模型版本，不允许把当前主角/技能名称加进中立验证器。
